# Olist与LaDe怎样一起用于智策

可以统一接入同一个系统，作为两个独立验证场景。当前没有证据可以把两份数据中的真实订单、包裹、商家或快递员一一对应，所以不做业务记录之间的强行连接，也不宣称它们来自同一家企业。

## 可以统一的部分

| 内容 | Olist场景 | LaDe场景 |
|---|---|---|
| 页面与智能体入口 | 经营指标、商家履约、历史订单风险 | 揽收任务、派送任务、时间窗及事件回放 |
| 原始事实 | 巴西电商订单、商品明细、付款、评价、配送日期 | 中国五城市包裹、快递员、接单及完成时间、事件位置与轨迹 |
| 工具约定 | 输入筛选条件，返回指标、分母、SQL与数据来源 | 已实现城市、月日、快递员筛选，返回真实指标、SQL及事件回放证据 |
| 复现机制 | 来源版本、原始哈希、数据库与独立复核 | 固定仓库版本、逐文件哈希、完整CSV解析及容器校验 |

后续可以在总控Agent中识别问题对应哪个数据源，再调用相应工具。当前LaDe已独立导入数据库并接入预算求解与真实事件回放，页面第⑩部分可操作；第⑪部分已加入LaDe单场景的原定四Agent受控协作，尚未实现跨来源自主编排。详见 [数据库与算法接入报告](LaDe数据库与算法接入报告.md) 和 [四Agent协作与验收](原定四Agent协作与验收.md)。

## 不可混为一谈的部分

- Olist的订单编号与LaDe的包裹/任务编号没有共同映射。实际已下载的LaDe城市CSV也使用 `order_id`，而发布方README将其称作 `package_id`。两个来源同样叫 `order_id`，也不能据此连接；字段归一化时需要显式登记这一差异，保留原始列名。
- LaDe的揽收与派送子集也需要单独检查关联键，不能默认属于同一包裹的连续全链路。
- Olist现有延迟指标比较实际送达日和预计送达日；LaDe-P可在有效样本上比较实际揽收时刻和要求的时间窗。两者应使用不同指标名与分母。
- 当前LaDe-D字段说明没有列出派送承诺截止时间，不能直接套用Olist的延迟标签。
- Olist销售金额使用BRL；已核查的LaDe字段没有对应成交额或真实加急费用，不填0凑金额，也不作跨币种合计。
- 不将Olist训练出的风险模型直接用于LaDe任务：特征、时间、区域和目标不同，需要新的训练和时间划分评估。
- 之前的200场景模拟对照仍属于模拟实验。下载真实历史记录不会自动使那些结果变成真实物流效果。

## 推荐的存储方式

```text
data/raw/                  原Olist九张CSV，保持不变
data/warehouse.sqlite      原Olist分析库，保持不变
data/lade/raw/             LaDe固定版本的完整原始文件
data/lade/provenance/      发布方文件清单、元数据与本地校验记录
data/lade/warehouse.sqlite 已建成的独立LaDe库，约5.30 GB
```

如将来希望在一个数据库连接中访问，可把两个SQLite库作为独立库挂接，使用 `olist.*` 和 `lade.*` 明确区分来源。任务唯一键应至少包含来源和子集，例如 `olist:order:ID`、`lade:pickup:city:package_id`；最终主键仍需在真实文件中检查唯一性。

可以统一“任务ID、来源、事件类型、发生时间、可见时间”的工具返回结构，但缺失的接收时间不可冒充真实记录。如果以事件发生时间作为历史回放中的可见时间，需要明确标注这个假设。实际城市CSV的时间示例是 `09-25 08:08:00`、`ds=0925`，未包含年份；未核实日历年份前不可自行填入2026年，也不可据此与Olist按自然日期连接。

LaDe已知提供时间窗和实际任务完成记录，可优先做一个城市的揽收时效试点。对未来完成事实必须按时间隔离，不能拿完成时间提前判断当前风险。真实干预费用及行动效果仍需额外数据，否则预算费用和行动结果应继续标为模拟。
