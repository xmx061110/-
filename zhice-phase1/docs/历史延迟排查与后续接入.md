# 历史配送延迟排查

本地助手新增第⑤部分。选择一个完整月份，可附加商品类别，商家保持“全部”，点击“生成排查清单”。无需模型也可运行这项统计。服务重新启动后生效。

清单先用事实表和原始表两条 SQL 分别计算各商家指标，任一复核失败即停止。参与排序的商家至少有30笔有效配送订单，并有观察到的延迟订单。按历史延迟订单数、延迟率依次降序排列，商家ID作为并列时的稳定顺序；这只是一个可解释的排查规则，尚未证明比其他规则更优。

命令行复现：

```powershell
python -m zhice.triage --month 2018-01
python -m zhice.triage --month 2018-01 --category beleza_saude --min-orders 30 --limit 10
```

输出 `reports/历史配送延迟排查清单.json`，包含筛选、排序规则、全体商家复核数量、清单及可单独执行的两份 SQL。第二次运行会覆盖该示例文件，可使用 `--out` 指定其他文件。接口为 `POST /api/triage`，仅允许 `month`、`category`，本地服务仍只允许本机访问。

商家关联的配送结果是订单级观察，多商家订单无法直接归责。建议仅是调查动作：核对交运时间、承诺送达时间和异常记录，确认后才决定干预。未计算收益、成本或实时风险，也未自动联系商家。

后续多智能体围绕“优先排查谁、证据是什么、还缺什么信息”展开：数据角色调用本模块；诊断角色只提出有证据支持的调查假设；建议角色列出可执行动作及所需条件；审核角色检查数字、归因和证据缺口。目前已实现的是数据工具与排查页面，尚未实现这四个模型角色，不能宣传为多智能体系统已完成。
