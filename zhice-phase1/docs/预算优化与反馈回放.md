# 预算优化与反馈回放：说明和验收记录

更新：2026-11-01。

后续迭代已加入稳定重规划、200场景四策略对照和第⑨部分交互复核，见 [滚动重规划优化报告](滚动重规划优化报告.md)。下文保留第一版预算算法及反馈回放的验收口径。

当前实现解决一个具体问题：给定候选订单、单笔处理费用和优先级效用，在预算内选择一组订单；收到反馈后，保留已支出费用，对未执行行动重新规划。

预算实验使用历史风险评分与模拟费用；反馈演示使用完全人工构造的订单和事件。当前没有接入真实物流，也没有验证催单或加急的真实效果。

## 运行方式

在 `zhice-phase1` 文件夹运行，Python 3.10或以上；重新生成批量评估需要Python 3.11或以上（使用 `hashlib.file_digest`）。当前电脑可以使用下列完整Python路径：

```powershell
$py = "$env:USERPROFILE/.cache/codex-runtimes/codex-primary-runtime/dependencies/python/python.exe"
& $py -m zhice.agent_server --port 8793 --open
```

第⑦部分选择下单日期和模拟预算，点击“比较预算分配方案”。第⑧部分点击“回放反馈并重新规划”，查看各轮方案和已支出金额。两项均无需模型密钥。端口被占用时可换一个本机端口。

```powershell
& $py -m zhice.budget_optimizer --day 2018-07-01 --budget-cents 30000 --seed 0 --limit 100
& $py -m zhice.feedback_replay
& $py -m work.evaluate_budget
& $py -m unittest discover -s tests -v
```

对应输出为 `reports/预算分配交互结果.json`、`reports/反馈回放示例.json`、`reports/budget-optimization-evaluation.json`。选单和目标可复现，耗时会随电脑负载变化。

本机接口：`POST /api/budget`，请求 `{"day":"2018-07-01","budget_cents":30000}`；`POST /api/feedback-demo`，请求 `{}`。反馈演示仅允许固定样例。自定义事件调用Python函数 `zhice.feedback_replay.replay(items, total_budget_cents, events, as_of)`。

## 预算算法与数据口径

这是经典0-1背包：每笔订单至多选一次，最大化选中订单的效用之和，费用不得超过预算。不宣称提出了新的基础算法。参考：[OR-Tools背包问题说明](https://developers.google.com/optimization/pack/knapsack)，本项目自行实现Python动态规划，未调用OR-Tools求解器。

工程处理包括：用费用最大公约数压缩金额单位；剪去费用更高且效用不更好的状态。费用使用整数分，效用使用非负整数；同分优先选择更低费用方案。精确最优仅针对传入候选、整数目标和预算约束，不代表实际经营最优。最多500笔候选，压缩后预算容量上限100000。

历史场景读取 `models/historical-risk-test.csv`，按指定日期的下单时间和订单ID排序取前100笔。此文件仅覆盖已送达且时间有效的历史测试订单，并非实时待处理队列。优化器不读取实际延迟标签和实际送达日期。

费用和系数由固定 `SHA256(seed:order_id)` 映射生成：处理费用1～30 BRL，假设干预系数0.2、0.5、0.8。前者不是原始运费或实际加急报价，后者未从真实干预估计。单笔效用为“未校准风险评分×假设系数×1000000”，逐单四舍五入为整数。

效用不能解释为预计挽回订单数、利润或投资回报。现有历史预测模型测试AUC约0.571，仍需改进。

## 预算实验结果

固定20个日期、3个种子、3种预算，共180个场景。每个场景各算法使用相同输入。

| 检查或比较 | 本次结果 |
|---|---:|
| 费用不超预算 | 180/180 |
| 与未剪枝精确动态规划目标一致 | 180/180 |
| 优于风险排序 | 180/180 |
| 优于效用/费用排序 | 123/180，其余相同 |
| 对效用/费用排序的平均相对目标增幅 | 0.30145% |
| 对风险排序的平均相对目标增幅 | 72.47696% |

## Inner Monologue如何用于本项目

[Inner Monologue论文项目页](https://inner-monologue.github.io/)研究将环境描述、执行成功或失败、人类反馈等信息加入后续规划输入，实验对象为机器人。论文结果不能直接作为本项目的物流效果证据。

本项目借鉴“接收反馈→更新已知事实与风险输入→重算剩余预算→复核→记录执行结果”的机制。当前未通过反馈自动训练模型，尚未实现论文中的完整LLM规划闭环。

| 原定角色 | 后续职责 |
|---|---|
| 总控Agent | 接事件，判断是否重规划，传递截止时间与状态版本 |
| 经营分析Agent | 根据当时可见信息更新风险评分，保留来源 |
| 优化决策Agent | 调确定性求解器，对未执行行动重排预算 |
| 方案评审Agent | 查超支、重复执行、过期状态和未来信息泄漏 |

网页第⑥部分是先前的历史排查角色实验，尚非上述原定四Agent架构。本报告记录算法原型交付时的范围。2026-11-02后续进展：第⑪部分已接通LaDe场景的原定四角色，详见 [四Agent协作与验收](原定四Agent协作与验收.md)；反馈发生后反复调用模型仍未实现。

## 反馈回放规则和示例

起点快照中的订单假设全部待处理；事件应发生于起点快照之后。事件包含唯一ID、订单ID、类型、发生时间、接收时间；时间必须带时区。按接收时间排序，同接收时间按事件ID排序。

- `observation`：更新状态，可附上上游提供的整数 `priority_units`。本模块不猜测“异常后风险增加多少”。
- `commit`：只执行当前方案中尚未执行的订单，立即锁定固定费用。
- `action_result`：记录成功或失败；失败不自动退款，不自动再次执行同一订单。

已送达和取消的订单退出候选；相同ID、相同内容的重复事件忽略，内容冲突报错。较旧或同发生时间的观察不覆盖新观察；截止之后才收到的事件不能影响当前方案；终态订单不可直接重新激活。

模拟预算50 BRL，A/B/C费用10/20/30 BRL，初始效用60/130/120：

| 步骤 | 尚未执行的选单 | 已支出BRL | 本轮计划费用BRL |
|---|---|---:|---:|
| 起始 | B、C | 0 | 50 |
| A异常，上游模拟效用改为200 | A、B | 0 | 30 |
| 执行A并扣费 | B | 10 | 20 |
| B确认送达 | C | 10 | 30 |
| A行动反馈失败 | C | 10 | 30 |

全部订单、状态、评分变化和行动结果均为人工构造。样例验证反馈响应与预算记账，不证明行动减少真实延误。边界测试覆盖重复与冲突事件、未来事件隔离、过期状态、重复执行、时区与输入不变性。

## 当前验收边界

完成静态预算求解、两条贪心基线、180场景对照、独立穷举、事件回放、逐轮费用证据和本地展示入口。尚未接真实物流订阅、在途节点模型、真实费用或干预效果；未实现持久化、并发事务和原定四Agent端到端协作。当前是纯函数原型，不用于直接控制外部物流行动。

本次全套回归测试62项通过，日志为 `reports/算法与反馈回归测试.log`，包括8项反馈回放测试及本机接口检查。未调用付费模型或真实物流服务。测试时将临时目录设在项目 `work/test-temp`；当前受限执行环境中的本机HTTP测试需允许本机网络访问，初次受限运行的环境错误不计为通过记录。

下一步可固定相同事件流，对比“不重新规划”“周期重规划”“事件触发重规划”，统计超支、重复执行、响应耗时、方案切换及模拟目标。真实延迟改善需真实行动结果与适当对照才能报告。

Olist只能回放它实际记录的下单、交接承运商和送达时间，没有完整实时扫描轨迹、催单结果、运力容量或干预费用，无法还原真实快运调度闭环。人为添加的故障和行动结果必须标为模拟。
